# ADR 0008: 更新競合には version 楽観ロックを採用する

## 決定

- task の更新競合は `version` による楽観ロックで検出する。
- 更新は取得時の version を条件に含める。更新対象がない場合は `409 Conflict` を返す。
- 後勝ち（last-write-wins）は採用しない。競合時は最新状態を取得し、ユーザーに再操作を促す。
- DnD など即時反映する操作は楽観的に更新し、永続化失敗時は表示をロールバックして通知する。

### 決定の理由

- 個人の複数端末で同じ task を同時に変更した場合でも、変更を無言で失わせない。
- 個人利用では競合頻度が低いため、初期段階で自動マージを実装する必要はない。
- DnD の表示を API の応答を待たずに反映することで操作感を維持できる。

## 不採用

- 後勝ち（last-write-wins）。
  - 別端末の変更を無言で上書きする。
- 悲観ロック。
  - ユーザー操作中にロックを保持する必要があり、複数端末の task 編集には重い。
- 初期からの自動マージ。
  - 競合頻度に比べて実装・検証の複雑さが大きい。

## 補足情報

### 背景

- D1 は唯一の正本 DB とし、複数行を更新する操作は transaction/batch で原子的に処理する。

### 制約事項

- 更新 SQL は `WHERE id = ? AND owner_id = ? AND version = ?` を条件に含め、成功時に version を 1 増やす。
- `409 Conflict` の API 形式、競合 UI、再試行の詳細は後続の要求または ADR で決定する。
